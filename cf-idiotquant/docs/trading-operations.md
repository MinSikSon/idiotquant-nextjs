# 자동매매 운영 현황

관리자 홈의 **자동매매 운영 현황** 또는 `/admin/trading`에서 조회한다.
매매·스캔·아카이브·스케줄러의 실제 기록을 표시하며 예시 데이터는 포함하지 않는다.
스케줄러 완료는 작업 **배정** 완료이며 병렬 계좌의 완료 상태는 각 실행에서 확인한다.

## 운영 반영 순서

1. Worker 저장소의 `0040_trading_operations.sql`, `0041_operation_snapshots.sql`까지 D1에 적용한다. 새 Worker 배포 전에 0041이 필요하다.
2. 프론트와 Worker 양쪽에 같은 `INTERNAL_JWT_SECRET`을 설정한다. 새 조회 API는 서명 키가 없으면 503으로 닫힌다. 기존 레거시 신원 헤더만으로는 조회할 수 없다.
3. Worker를 배포한 뒤 프론트를 배포한다.
4. 다음 예약 실행 후 관리자 화면에서 단계 기록을 확인한다. 기존 실행은 소급 생성하지 않는다.

이 작업에서는 운영 마이그레이션이나 배포를 실행하지 않았다.

## 기록과 상태

- `operation_runs`는 실행별 ID·부모 스케줄 실행·국가·사용자 ID·상태를 저장한다. `steps_json`에 반복 종목별 단계를 순서대로 묶어 저장한다. 이전 버전의 `operation_steps` 기록도 계속 조회한다.
- 실행 시작과 종료에 저장하며, 실행 중에는 시작 시점의 단계가 표시된다. 최종 단계 상세는 종료 후 반영된다. 런타임 강제 종료 시에는 시작 기록만 남을 수 있다. 완료된 미장 수집·아카이브, OFF 계좌의 반복 기록은 생략한다.
- 완료·실행 중·일부 실패·실패·생략을 구분한다. 인증 실패 시 적립과 결과 저장이 성공해도 전체 성공으로 덮지 않는다.
- 10분 이상 갱신되지 않은 실행은 **확인 불가**다. 완료·실패로 추정하지 않는다. 스케줄 진입이 3분 이상 없으면 상단에 별도 표시한다.
- 종목 스캔은 종목별 수집·지표 계산을 한 단계로 기록한다. 상세에는 실제 호출 함수와 서비스 구성을 표시한다. 매매는 시세·재무·조건 판단·주문·접수 기록을 각각 기록한다.
- 주문 접수와 실제 체결을 구분한다. 주문 로그 저장 실패 후 주문을 다시 보내지 않는다.
- 계좌번호·키·토큰·원본 응답·원본 예외 메시지는 관찰 기록에 저장하지 않는다. 운영 필드 허용 목록과 고정 사유 코드만 저장한다.
- 기록 저장이 실패하면 해당 실행의 관찰 저장을 중단하고 업무는 계속한다. 기존 매매 로직의 포인트·재시도·보유 수량 정책을 따른다.

## 조회와 보관

`GET /admin/trading/status`, `/admin/trading/runs`, `/admin/trading/runs/:id`를 기존 프록시로 호출한다.
서명된 신원과 DB의 관리자 역할을 확인하며, 프론트 페이지와 프록시도 관리자 권한을 검사한다.
응답과 프록시의 백엔드 조회는 `no-store`다. 기록은 최근 24시간만 조회하며 매 정각 최대 2,000개의 만료 실행을 단계 기록과 함께 정리한다.
목록은 50건씩 안정적인 `(started_at, id)` 커서로 조회한다. 국가는 KR·US, 작업은 trade·scan·archive·scheduler이며 사용자 ID로도 필터할 수 있다.

화면 표시 중 5초마다 조회하며 숨겨지면 조회를 중단한다. 이전 요청이 진행 중이면 다음 폴링을 건너뛴다.
선택 변경 시 요청을 중단하고, 조회 실패 시 기존 데이터와 실패 안내를 함께 표시한다.

## 기록량 산정

실행 1건은 시작·종료에 `operation_runs` 한 행을 각각 기록하며, 단계별 추가 행을 만들지 않는다. 단계 상세는 JSON으로 보존한다. 보관기간이 끝나면 실행 한 행만 삭제한다. 기존 단계 기록은 원래 방식으로 함께 정리한다.

국장 7종목 정상 배치는 테이블 행 변경이 38회에서 2회, 보관기간 만료 삭제는 13행에서 1행으로 감소한다. 스케줄러·국장 스캔·이미 완료된 아카이브의 반복 로그 및 삭제를 하루로 환산하면 약 63,072행에서 6,912행으로 약 89% 줄어든다. 인덱스 쓰기·실제 아카이브·자동매매·사용자 작업을 제외한 비교이며, 실제 과금 수치는 `meta.rows_written`과 D1 Metrics로 확인해야 한다. 이전 로그가 남은 첫 24시간에는 정리 비용이 더 발생할 수 있다.

## 검증

- 프론트 린트·타입 검사·전체 테스트·프로덕션 빌드.
- Worker 전체 테스트·배포 dry-run.
- 실제 workerd·로컬 D1에서 프론트가 발급한 JWT, DB 관리자 권한, 실행 단계 조회와 민감 필드 제외 검증.
- 브로커를 대체한 실제 매매 함수에서 주문 접수·거절·예산 부족·포인트 차감 회귀 검증.
- 실제 스캔 함수에서 API 오류 기록·커서 보존, 실제 아카이브 함수에서 저장 실패 후 삭제 생략 검증.
- 실제 화면 컴포넌트를 테스트 응답으로 렌더링해 단계 선택, 국가·작업 전환, 오류 시 데이터 유지, 미갱신, 숨김 시 폴링 중단, 모바일 320px 및 다크 모드 확인.
