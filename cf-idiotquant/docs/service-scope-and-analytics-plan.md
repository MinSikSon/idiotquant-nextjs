# 서비스 정리 후보와 페이지 이용 통계 설계

작성일: 2026-11-07
상태: 구조 정리 1차 적용. 통계 수집·운영 설정 변경은 수행하지 않았다. 아래 설계 표는 정리 전 조사 기준이며 적용 내역은 11절에 기록한다.

## 1. 목적과 판단 원칙

새 재방문 기능을 붙이기 전에, 기존 서비스 중 유지·축소·통합·분리할 대상을 판단한다.
방문 수만으로 삭제하지 않고 접근 가능 대상, 메뉴 노출, 실제 기능 사용, 다음 행동,
반복 이용, 유지 비용을 함께 본다. 아래 우선순위와 관찰 기간은 운영 데이터가 없는 상태의 제안이다.

- 핵심 흐름 가설: 종목 발굴 → 비교 → 분석 → 관심종목 저장 → 다시 확인.
- 구조 정리와 제품 삭제를 구분한다. 중복 URL의 구현을 정리해도 기존 주소의 이동은 보존한다.
- 관리자 전용·미공개·차단된 기능은 일반 사용자 이용률 비교에서 제외한다.
- 수집 시작 전 기록은 소급 생성하지 않는다. 미수집·수집 장애·정상 0건을 구분한다.
- 이용이 적어도 검색 유입, 특정 사용자의 반복 이용, 법적 고지, 운영 필수 역할이 있으면 별도 평가한다.

## 2. 현재 확인한 상태

| 항목 | 코드에서 확인한 내용 | 판단상의 의미 |
| --- | --- | --- |
| 관리자 | `/admin`은 회원 현황·설정, `/admin/trading`은 자동매매 운영 현황 | 페이지 이용 통계 화면은 별도 필요 |
| 검색 기록 | `lib/features/searchLog/`는 종목 검색·인기 종목용 | 전체 페이지 방문 수나 유저 수로 대체할 수 없음 |
| 인프라 사용량 | `components/profile/usageCard.tsx`는 관리자용 D1·KV 사용량 표시 | 사용자 행동 통계와 목적이 다름 |
| 페이지 계측 | 검토한 소스에서 전역 페이지뷰 수집기를 찾지 못함 | 외부 대시보드 설정과 과거 로그 보유 여부는 미확인 |
| 접근 제한 | `middleware.ts`에서 `/balance*`는 관리자만 접근, `/backtest*`는 `/screener`로 이동 | 접근 제한 때문에 낮은 이용을 제품 수요 부족으로 해석하지 않음 |
| 관심종목 변화 | 스크리너 관심종목 모드에 변화 표가 있음 | 기존 기능의 발견·이용 여부를 먼저 측정 |
| 자원 사용 | UsageCard에 DB 한도 초과로 로그인 장애를 겪었다는 주석이 있음 | 통계 수집이 핵심 서비스 저장·인증에 부담을 주지 않아야 함 |

이 문서는 현재 작업본 기준이다. 과거 점검 보고서의 문제를 현재에도 남아 있는 것으로 간주하지 않는다.

## 3. 덜어낼 후보

### A. 이용 통계와 별개로 검토할 구조 정리

| 우선 | 후보 | 제안 | 삭제·변경 전에 확인할 것 |
| --- | --- | --- | --- |
| 높음 | `/search` 이동 페이지 | `next.config.mjs`의 `/analyze` 리다이렉트와 중복하는 페이지 구현 정리 | 검색 훅·컴포넌트는 분석 화면이 사용하므로 route group 전체 삭제 금지. 쿼리·북마크 유지 |
| 높음 | `/algorithm-trade`, `/balance-kr`, `/balance-us`, `/game` | 호환 주소로 분류하고 이동 처리 방식 단순화 | `/balance`의 국가·계좌 선택 쿼리와 `/game`의 쿼리 보존, 인증 동작 유지 |
| 높음 | 비활성 `/backtest` UI | 현재 차단 상태를 명시하고 복구 계획이 없다면 페이지·전용 코드 정리 후보 | middleware에서 실제 비활성화됨. 스크리너와 공유하는 계산·API·테스트는 사용처 조사 후 판단 |
| 유지 | 목표 비중 리밸런싱 | 어드민 전용 자동매매의 추후 구현 페이지로 유지. 삭제 후보에서 제외 | `components/balance/groupStrategyEditor.tsx`, 기존 적용 전략·저장값 유지 |
| 중간 | 제작 게임 프로토타입·정적 HTML | 실험 목록으로 분리하고 공개 서비스 동선에서는 제외 검토 | `/games/crafting-prototype`, `public/crafting-prototype*.html`의 외부 링크·테스트 목적 확인 |
| 중간 | 미사용 slice/API·의존성 | 참조가 없는 항목만 후속 코드 정리 | `filter`, `fmpUsMarket`, `timestamp` 등은 후보일 뿐. 동적 import·테스트·스크립트까지 참조 조사 필요 |

### B. 데이터를 수집한 뒤 판단할 제품 범위

| 대상 | 축소·분리 가설 | 반드시 함께 볼 데이터 | 초기 제안 |
| --- | --- | --- | --- |
| 게임 `/games` | 주식 발굴 도구와 목적이 다른 별도 제품일 수 있음 | 게임 반복 이용, 투자 도구와의 양방향 이동, 운영 비용 | 게임 이용자층이 별도라면 삭제보다 분리 검토 |
| 가계부 `/ledger` | 독립적인 자산 관리 도구 성격 | 로그인 사용자 중 방문 비율, 실제 저장 성공, 주간 반복 이용 | 소수여도 반복 저장하면 유지 가치가 있을 수 있음 |
| 계산기 `/calculator` | 메뉴를 차지하는 독립 도구가 필요한지 | 계산·저장 성공, 분석 화면과의 이동, 검색 유입 | 이용이 적으면 분석 화면의 보조 도구로 통합 검토 |
| 퀀트 안내 `/quant` | 자주 방문하는 도구보다 유입용 콘텐츠 | 외부 진입, 스크리너·분석으로 이어진 세션 | 재방문이 적다는 이유로 삭제하지 않음 |
| 프로필의 점수·시각화 | 계정 관리와 관심종목 확인을 복잡하게 하는지 | 해당 영역 노출·상호작용, 관심종목 분석 진입 | 핵심 행동과 연결이 약하면 접기·이동 검토 |
| 스크리너의 고급 패널 | 기본 발굴 흐름의 복잡도를 높이는지 | 패널 노출·사용, 필터 저장, 비교·분석 이동 | 기본 화면은 핵심 조건 중심, 고급 기능은 접기 검토 |

약관·개인정보 처리방침·로그인·초대 수락·운영 관리 기능은 방문 순위로 삭제하지 않는다.
홈·발굴·비교·분석·관심종목은 핵심 흐름 가설에 포함하되, 개별 패널은 별도 평가한다.

## 4. 페이지 분류표

집계 키는 URL 원문 대신 아래 허용 목록을 사용한다. 동적 토큰·공유 데이터·쿼리는 저장하지 않는다.

| 집계 키 | 실제 경로 | 접근·용도 | 집계 방식 |
| --- | --- | --- | --- |
| home | `/` | 공개 | 제품 통계 |
| screener | `/screener` | 공개, 일부 로그인 기능 | 제품 통계 |
| compare | `/compare` | 공개, 회원별 한도 차이 | 제품 통계 |
| analyze | `/analyze` | 공개, 일부 로그인 기능 | 제품 통계 |
| calculator | `/calculator` | 공개 | 보조 도구 |
| quant | `/quant` | 공개 콘텐츠 | 유입·다음 행동 중심 |
| games | `/games` | 공개 게임 | 투자 도구와 별도 그룹 |
| crafting_prototype | `/games/crafting-prototype` | 공개 실험 | 실험 그룹 |
| ledger | `/ledger` | 로그인 필요 | 로그인 사용자 기준 |
| ledger_join | `/ledger/join/[token]` | 로그인 필요 | 토큰 제거, 초대 동선 |
| profile | `/profile` | 로그인 필요 | 로그인 사용자 기준 |
| balance | `/balance` | 관리자 전용 | 내부 운영 그룹 |
| share | `/share` | 공개 | 공유 내용 제외 |
| login | `/login` | 공개 | 인증 동선 |
| terms / privacy | `/terms`, `/privacy` | 공개 | 필수 고지 그룹 |
| admin / admin_ticker_map / admin_trading | `/admin`, `/admin/ticker-map`, `/admin/trading` | 관리자 전용 | 내부 운영 그룹 |
| 호환 주소 | `/search`, `/algorithm-trade`, `/balance-kr`, `/balance-us`, `/game`, `/game/roguelike` | 이동용 | 도착 페이지만 제품 PV로 집계 |
| 비활성 주소 | `/backtest` 및 하위 | 발굴로 이동 | 제품 기능으로 집계하지 않음 |

`public/`의 HTML은 Next.js 공통 레이아웃 계측으로 수집되지 않는다. 프로토타입은 별도 실험 목록에
표시하고, 수집기를 명시적으로 붙이기 전에는 ‘미계측’으로 표시한다. API·정적 자원·404는 제품 페이지 순위에서 제외한다.
공개 여부는 메뉴 표시가 아니라 서버의 접근 정책을 기준으로 관리한다.

## 5. 통계 정의

### 첫 버전에 포함할 지표

| 지표 | 정의 |
| --- | --- |
| 페이지뷰(PV) | 실제 화면 진입 1회. 새로고침·뒤로 가기·재진입 포함. query/hash만 바뀌면 추가 PV 없음 |
| 방문 브라우저(UV) | 선택 기간에 같은 무작위 브라우저 식별자를 중복 제거한 수. 사람 수라고 부르지 않음 |
| 로그인 이용 계정 | 서버 세션에서 확인한 계정을 가명 처리해 기간 내 중복 제거. 관리자 제외 |
| 세션 | 같은 브라우저에서 30분 이상 이벤트가 없으면 새 세션. 자정에는 임의 분리하지 않음 |
| 첫 진입 / 마지막 관측 페이지 | 세션 첫·마지막 페이지. 마지막 관측은 종료 확정이나 사용자 불만을 뜻하지 않음 |
| 기능 실행 세션 비율 | 해당 페이지의 성공 행동이 1회 이상 있는 세션 ÷ 해당 페이지 방문 세션 |
| 페이지 이동 | 같은 세션에서 연속으로 관측된 서로 다른 대표 페이지 간 이동 |
| 다른 날 재이용 | 선택 기간 중 같은 페이지를 KST 기준 2일 이상 이용한 브라우저·계정 수 및 비율 |

UV는 날짜별 UV를 더해 만들지 않는다. 기간 전체에서 다시 중복 제거한다.
페이지별 UV의 합도 서비스 전체 UV와 같지 않다. 익명 방문과 로그인 계정을 합쳐 ‘전체 사람 수’로 표시하지 않는다.
쿠키 거부·차단·삭제·시크릿 모드·여러 기기로 인한 누락과 분리는 화면에 설명한다.
계정 식별이 없는 방문은 익명/식별 불가로 분류하고 로그인 사용자 재방문 지표와 분리한다.

### 핵심 행동 허용 목록

| 페이지·영역 | 성공 이벤트 | 의미 |
| --- | --- | --- |
| 발굴 | `filter_saved` | 이름 붙인 필터 저장 성공 |
| 분석 | `analysis_loaded` | 선택 종목의 대표 시세 조회 성공. 클릭이나 로딩 시작과 구분 |
| 관심종목 | `watch_added` | 관심 저장 API 성공. 제거·반복 클릭은 제외 |
| 비교 | `comparison_loaded` | 사용자 요청에 따른 종목 추가 조회 성공. 저장본 복원은 별도 |
| 계산기 | `calculation_completed` | 유효 입력으로 명시적 계산 실행 성공. 입력 변경 횟수와 구분 |
| 가계부 | `ledger_entry_saved` | 내역 저장 성공. 금액·메모 제외 |
| 게임 | `game_run_started`, `game_run_finished` | 새 판 시작과 종료. 저장된 판 불러오기는 신규 시작에서 제외 |
| 공유 | `share_link_copied` | 링크 복사 성공. 공유 패널 열기와 구분 |

초기에는 모든 클릭·스크롤·키 입력을 추적하지 않는다. 고급 패널·프로필 시각화 정리를 판단할 때만
해당 영역의 `feature_exposed`·`feature_used`를 제한적으로 추가한다. 미계측 영역은 이용 0건으로 표시하지 않는다.
클라이언트 성공 이벤트는 관측용이며 매매 체결·회계 기록의 원장으로 사용하지 않는다.

## 6. 관리자 화면 제안: `/admin/analytics`

- 기본 기간 최근 28일, 빠른 선택 7일·28일·90일, KST 날짜 범위. 전 기간은 수집 시작일 이후만 선택.
- 기본 제품 그룹은 일반 사용자, 운영 관리자 방문은 제외. 익명·로그인·기기 구분 제공.
- 상단: PV, 방문 브라우저, 로그인 이용 계정, 다른 날 재이용, 수집 상태·최신 반영 시각.
- 페이지 표: 페이지명, 접근 대상, 방문 세션, UV, PV, 첫 진입, 기능 실행 세션 비율,
  다른 날 재이용, 직전 동일 기간 증감, 판단 상태.
- 상세: 일별 추이, 앞뒤 페이지, 성공 행동별 건수·실행 세션 수. 기능 실행 정의를 함께 표시.
- 로그인·필수 고지·내부 운영·실험 그룹은 별도 탭. 페이지 집계가 0이어도 목록에 남김.
- 정리 후보 탭: 유지/축소/통합/분리/종료 검토/판단 보류, 근거·담당자·다음 검토일 기록.
- CSV는 집계값만 내보냄. 개인별 방문 이력·이름·이메일을 보여주는 화면은 첫 버전에서 제외.

관리자가 일반 사용자 미리보기를 켜도 실제 admin 방문은 제품 통계에서 제외한다.
관리자 조회 API는 화면 숨김과 별개로 서버 세션 역할을 검증하고 캐시 공유를 막는다.

## 7. 수집·저장 구조 제안

브라우저 → 동일 출처의 수집 API → 별도 통계 저장소 → 관리자용 집계 API → 관리자 화면.
현재 프록시가 Worker로 요청을 전달하는 구조를 활용하되, 공개 수집 API와 관리자 조회 권한을 분리한다.
API 이름은 제안이며 기존 기능에 추가하지 않았다.

- `POST /api/public/analytics`: 허용된 페이지·행동만 수신. 로그인 없이 동작해야 함.
- `GET /api/admin/analytics`: Next.js 서버에서 관리자 확인 후 통계 조회. 백엔드에서도 신뢰된 신원 검증.
- `GET/PATCH /api/admin/analytics/reviews`: 페이지별 정리 검토 기록 관리.
- Next.js 루트의 작은 클라이언트 수집기가 최초 화면·App Router 이동·뒤로 가기를 감지.
- 인증 로딩 완료 후 방문자 구분을 결정해 동일 화면을 익명/회원 두 번 기록하지 않음.
- 탭이 실제 표시된 시점에 전송. prefetch·SSR·리다이렉트 중간 화면은 PV를 만들지 않음.
- 페이지 진입마다 무작위 `page_view_id`, 이벤트마다 `event_id` 부여. 재전송은 같은 ID를 사용하고 서버에서 중복 제거.
- 클릭·성공 이벤트는 해당 page_view_id와 연결. 여러 탭의 이동 순서가 섞이지 않도록 tab_id 포함.
- 요청 본문 크기·허용 이벤트·빈도 제한, 동일 출처 검증, 봇·합성 테스트 분리. 봇 제거는 완벽하다고 표시하지 않음.
- 네트워크 실패 시 작은 한도의 재시도만 수행. 계측 실패가 화면 동작·로그인·주문을 막지 않음.
- 명시적 수집 on/off, 비운영 환경 기본 off, 저장소 접근 불가 시 식별 불가 상태 처리.

저장할 값: 이벤트 ID, 대표 페이지 키, 허용 행동 키, 서버 수신 시각, 세션·탭·페이지뷰 ID,
브라우저 무작위 ID의 서버 가명값, 로그인 계정의 서버 가명값(선택), 서버 확인 사용자 구분,
기기 범주, 허용 목록 기반 이전 페이지 키, 계측 버전. 클라이언트의 userId·role은 신뢰하지 않는다.

저장하지 않을 값: URL 쿼리/hash·전체 referrer·초대 토큰·계좌 키·공유 payload·검색어·가계부 금액/메모·
이름·이메일·원본 IP·원본 User-Agent. 유입은 필요한 경우 referrer에서 허용한 도메인 범주만 추출한다.

식별자는 무작위 브라우저 쿠키를 기본 제안으로 하며 지문 수집은 하지 않는다. 로그인 계정은 서버 키로 가명 처리한다.
로그인 전후 식별자를 결합한 전체 사람 수는 만들지 않는다. 계정 기반 통계는 탈퇴 시 연관 원본 삭제가 가능해야 한다.
원본 보관 90일·식별자 없는 일별 집계 13개월을 초안으로 제안한다. 구현 전 보관·안내 정책을 확정한다.
쿠키 선택·수집 거부 처리와 개인정보 처리방침의 이용 목적·수집 항목·보유 기간을 실제 구현과 함께 검토한다.

### 저장소 선택과 비용 통제

첫 후보는 별도 통계 D1에 제한된 이벤트를 저장하고 일별 집계를 만드는 방식이다.
추가 외부 분석 서비스·메시지 큐·범용 이벤트 시스템은 첫 설계에 넣지 않는다.
다만 현재 요금제·실제 계정 한도 여유를 확인하기 전에는 D1 채택을 확정하지 않는다.

DB 분리는 데이터·쿼리 경합 범위를 줄이는 제안이며, 같은 계정의 할당량을 완전히 격리한다는 뜻이 아니다.
공식 문서는 D1의 계정별·DB별 제한과 DB 단위 쿼리 처리 특성을 구분한다.
인증 DB 재사용을 피하고 수집량 상한·읽기/쓰기 예산·중단 스위치를 함께 검증한다.
[D1 공식 문서](https://developers.cloudflare.com/d1/), [D1 제한](https://developers.cloudflare.com/d1/platform/limits/).

일별 집계 후보: page_daily(PV·행동 수·세션 수), actor_page_daily(기간 UV·재이용 계산용, 식별 보관 기간 내),
transition_daily(탭 내 페이지 이동), page_reviews(검토 상태). 원본 ID 중복 제거와 집계 반영은 일관되게 처리한다.
가명 ID가 남은 actor_page_daily는 익명 장기 집계가 아니므로 원본과 같은 삭제 정책을 적용한다.
집계는 재실행해도 중복 증가하지 않아야 한다. 여러 날 UV는 actor_page_daily에서 기간 중복 제거한다.
90일 초과 범위는 PV·행동 건수 등 식별자 없는 집계만 제공하고, 정확한 기간 UV·재방문은 제공하지 않는다.

대안인 Cloudflare Web Analytics는 페이지뷰·방문 개요를 빠르게 얻는 보조 수단으로 검토할 수 있다.
이 문서의 성공 행동·계정별 반복 이용·정리 검토 기록까지 대체하는 것으로 가정하지 않는다.
[Web Analytics 소개](https://developers.cloudflare.com/web-analytics/about/).
Analytics Engine을 선택한다면 샘플링에 따른 추정치를 명시하고 작은 기능의 정확한 이용자 수와 혼동하지 않는다.
[Analytics Engine 샘플링](https://developers.cloudflare.com/analytics/analytics-engine/sampling/).

## 8. 정리 의사결정 운영

1. 구조 정리 후보의 사용처·호환 링크 확인을 먼저 진행한다. 실제 삭제는 별도 작업으로 결정.
2. 계측 검증 후 최소 4주 관찰한다. 거래일·주말을 포함하고, 수집 장애일·공개 범위 변경일을 표시한다.
3. 페이지마다 접근 대상·메뉴 노출·방문·성공 행동·반복 이용·다음 이동·유지 비용을 한 장으로 검토한다.
4. 방문 적음 + 노출 적음이면 메뉴 발견성부터 확인한다. 방문 많음 + 행동 적음이면 기능·사용성 점검 우선.
5. 방문 적음 + 반복 이용 높음이면 소수 핵심 사용자의 도구로 유지·분리 검토.
6. 충분히 노출됐는데 방문·성공 행동·반복 이용이 모두 낮고 비용이 높으면 축소·종료 후보로 올린다.
7. 메뉴 이동/접기부터 단계적으로 바꾸고 변경일을 기록한다. 이후 관찰로 직접 URL 이용·핵심 흐름 변화를 확인한다.
8. 최종 종료 시 저장 데이터 처리·대체 동선·기존 링크를 검토한다. 순위표가 자동으로 기능을 삭제하지 않는다.

표본이 적으면 분모와 실제 건수를 함께 보고 ‘판단 보류’로 남긴다. 일률적인 이용률 컷오프는 아직 정하지 않는다.
기능 종료 전후 비교는 유입·장세·노출 변경의 영향을 받으므로 인과관계로 단정하지 않는다.
